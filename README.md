## 💡 Design Patterns

### Creational Patterns

1. **Factory Pattern**  
   A pattern used to instantiate objects without exposing the creation logic to the client.

2. **Singleton Pattern**  
   Ensures that a class has only one instance and provides a global point of access to it.

3. **Builder Pattern**  
   Helps in constructing complex objects by separating the construction and representation process.

4. **Prototype Pattern**  
   Used to create objects based on a template of an existing object through cloning.

---

### Structural Patterns

1. **Decorator Pattern**  
   Dynamically adds behavior or responsibilities to an object without modifying its structure.

2. **Adapter Pattern**  
   Allows two incompatible interfaces to work together by converting the interface of a class into another interface.

3. **Facade Pattern**  
   Provides a simplified interface to a complex system of classes, libraries, or frameworks.

4. **Proxy Pattern**  
   Controls access to an object, potentially adding additional functionality before or after the request gets to the real object.

5. **Flyweight Pattern**  
   Reduces the number of objects created and improves performance by sharing objects in certain contexts.

---

### Behavioral Patterns

1. **Observer Pattern**  
   Establishes a one-to-many dependency between objects, so when one object changes state, others are notified.

2. **Strategy Pattern**  
   Enables selecting an algorithm at runtime from a family of algorithms.

3. **Command Pattern**  
   Encapsulates a request as an object, thereby allowing parameterization of clients with different requests.

4. **Chain of Responsibility Pattern**  
   Lets multiple objects handle a request without coupling the sender and receiver, passing the request along the chain.

5. **State Pattern**  
   Allows an object to alter its behavior when its internal state changes.

6. **Mediator Pattern**  
   Reduces the dependencies between objects by handling their communication through a mediator object.

7. **Template Method Pattern**  
   Defines the skeleton of an algorithm, with steps deferred to subclasses, allowing customization of the process.

8. **Iterator Pattern**  
   Provides a way to access the elements of an aggregate object sequentially without exposing its underlying representation.

## ❓ Why Use Design Patterns?

- **Code Reusability**: Write DRY (Don't Repeat Yourself) code that can be reused across different parts of your project.
- **Maintainability**: Patterns make it easier to debug, extend, and refactor code.
- **Scalability**: Design patterns help structure your application for easy scaling as requirements grow.
